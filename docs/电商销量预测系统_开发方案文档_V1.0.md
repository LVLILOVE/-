## 第一章 产品定位、目标用户与核心价值主张

### 1.1 一句话定位

一个面向电商中小商家的**零门槛销量预测 Web 应用**：运营人员上传历史销量 CSV，系统自动完成数据清洗、特征工程与 LSTM 多步预测，直接给出未来若干天的销量曲线、误差指标与可导出的预测表，用来指导补货与分仓。

✅ 依据：任务书 2.1 总体目标「用户通过浏览器上传历史销量数据，系统自动完成特征工程并预测未来若干天的销量，输出预测曲线与误差指标，辅助补货与仓储规划」。

### 1.2 目标用户与典型场景

| 用户角色 | 是否 MVP 服务对象 | 核心诉求 | 典型使用场景 |
|---|---|---|---|
| 电商运营 / 补货专员 | ✅ 主用户 | 想知道"下周该备多少货"，不想也不懂写代码 | 每周固定一次，上传最新销量表 → 拿到未来 7/14/30 天预测 → 按预测调整采购单 |
| 仓储 / 分仓规划人员 | ✅ 主用户 | 判断各仓库货量分配 | 大促前，按仓库维度看预测曲线，决定主仓与前置仓铺货比例 |
| 中小商家老板 | ⚠️ 次要用户 | 要一个能看结论的简版视图 | 只看汇总指标与曲线，不参与数据准备 |
| 课程评审 / 答辩老师 | ✅ 隐性用户 | 验证技术方案完整性与真实性 | 现场演示一遍完整链路 |
| 数据科学家 | ❌ 非目标用户 | 需要深度调参与模型可解释性 | 本项目不提供，理由是任务书定位为"无需掌握编程技能" |

### 1.3 核心价值主张

1. **免编程**：全流程 Web 化，无需 Python 环境、无需写 SQL。
2. **端到端自动化**：把"清洗 → 插补 → 特征工程 → 建模 → 评估 → 可视化"打包成一次上传后的自动流程，这是相对"Excel + 手工移动平均"的主要代差。
3. **结果可度量**：不输出一个孤零零的预测值，而是同时给出 MAE / RMSE / MAPE 三个指标，并与移动平均基线对比，让用户知道"这个预测值可不可信"。
4. **结论可落地**：预测结果支持导出，能直接并入现有补货流程，而不是停留在网页上看。
5. **案例示范价值**：以菜鸟"需求预测与分仓规划"公开数据集为基准，结果可复现、可对标。

### 1.4 明确不做什么（本期范围红线）

以下内容**不做**，避免开发过程中范围蔓延导致延期：

- ❌ 实时/流式销量接入（对接 ERP、电商后台 API 等）——只做 CSV 文件上传。
- ❌ 自动补货下单、库存联动、"一键采购"等决策执行类功能。
- ❌ 多租户 SaaS 化、组织架构、权限角色体系（本期只有"注册用户"一种角色）。
- ❌ 移动端原生 App（响应式 Web 即可满足任务书要求）。
- ❌ 模型在线增量训练 / 自动重训调度（属于 V2.0 迭代项）。
- ❌ **用户上传后即时训练模型** —— 📌 受 1 分钟等待上限约束，LSTM 训练在物理上无法在该时限内完成。系统统一使用预训练模型推理，具体见附录 C-3。

### 1.5 关键成功指标

| 指标类别 | 指标 | 目标值 | 来源 |
|---|---|---|---|
| 算法效果 🔒 | 加权 MAPE | ≤ 20% | 任务书 2.2-3；口径见 📌 附录 C-1 |
| 算法效果 🔒 | 加权 MAE / RMSE 相对移动平均基线 | 降低 ≥ 15% | 任务书 2.2-3；基线为移动平均 📌 |
| 算法效果 📌 | 达标序列占比（逐序列 MAPE ≤ 20% 的序列数占比） | ≥ 60%（参考值，非硬卡点） | 本文档建议，需评审确认 |
| 产品可用性 🔒 | 单次预测任务端到端耗时 | **≤ 1 分钟** | 📌 项目负责人确认 |
| 产品可用性 | 用户从上传到看到曲线所需操作步数 | ≤ 5 步 | ⚠️ 本文档建议值 |
| 数据质量 | 上传文件校验前置拦截率 | 100%（字段缺失/格式错误在入库前拦截） | ✅ 任务书 2.2-1 |
| 数据质量 📌 | 预测覆盖率如实披露 | 100%（L1/L2/L3 序列数与占比必须在结果页展示） | 配合三级降级策略 |
| 兼容性 🔒 | 主流浏览器最新两个版本可正常使用 | Chrome / Firefox / Safari / Edge | 任务书 5.1、6.4 |

## 第二章 核心业务流程

### 2.1 主干路径（Happy Path）

以下为主流程，每一步都标注了**责任模块**与**失败时的分支出口**。

```
[1] 访问站点
     ├─ 未登录 ──→ 跳转登录页 ──→ [2]
     └─ 已登录 ──→ 直接进入工作台 ──→ [3]

[2] 用户注册 / 登录
     ├─ 注册：邮箱 + 密码 → 校验唯一性 → 写入 users → 自动登录
     └─ 登录：校验密码哈希 → 签发 Token → 前端本地存储
     ✗ 分支：密码错误 3 次 → 提示冷却；账号不存在 → 引导注册

[3] 进入「新建预测任务」
     ├─ 方式 A：上传自己的 CSV 文件
     └─ 方式 B：一键加载内置示例数据（菜鸟数据集抽样）

[4] 数据校验（系统自动，秒级返回）
     校验项：必需字段完整性 / 日期可解析 / 时间连续性 / 销量非负
     📌 仓库列为**必需字段**（任务书数据集必含仓库维度），缺失即拒绝
     ✗ 分支 A：字段缺失 → 返回具体缺失列名与期望格式 → 回到 [3]
     ✗ 分支 B：时间有断档 → 提示断档区间，用户选择「自动插值补齐」或「放弃」
     ✗ 分支 C：存在负值/异常尖峰 → 提示将按截断规则处理 → 用户确认后继续
     ✗ 分支 D 📌：序列数超上限 → 提示需筛选商品后重试（上限见 6.3 R5）

[5] 选择预测参数
     - 预测粒度：仓库 × 商品（📌 主粒度）/ 商品级汇总视图
     - 预测步长：未来 7 / 14 / 30 天（默认 7）
     - 是否纳入节假日特征：是 / 否（默认是）
     📌 不含"是否重新训练"选项 —— 统一使用预训练模型（见附录 C-3）
     → 提交任务

[6] 后端执行预测流水线（📌 目标 ≤ 1 分钟，见附录 D 实测）
     6.1 缺失值线性插值填补
     6.2 异常销量尖峰截断（阈值法）
     6.3 归一化（📌 按序列独立做，不做全局归一化）
     6.4 滑动窗口切分样本
     6.5 特征构造：星期、月份、节假日、滞后销量、滚动均值
     6.6 📌 序列三级分级（L1 仓库×商品 / L2 商品级 / L3 不可预测），见附录 C-2
     6.7 📌 计算移动平均基线（全量覆盖，用于对照与兜底）
     6.8 📌 加载**预训练** LSTM 模型，批量推理（不训练）
     6.9 计算加权 MAE / RMSE / MAPE + 达标序列占比，与基线对比（口径见附录 C-1）
     ✗ 分支：任一环节异常 → 任务置为「失败」+ 记录错误原因 → 前端可重试
     ✗ 分支：总耗时超 1 分钟 → 中止并返回"数据量过大"提示（软失败）

[7] 结果展示
     - 折线图：历史销量实线 + 预测曲线虚线（可选置信提示）
     - 指标卡：加权 MAE / RMSE / MAPE + 相对基线提升百分比
     - 📌 覆盖率披露：L1 / L2 / L3 序列数与占比
     - 分商品预测表格（📌 标注每条的 granularity_level 与置信度）
     ✗ 分支：加权 MAPE > 20% → 页面显著位置提示"本次预测误差偏高，建议谨慎参考"，并给出可能原因（数据量不足 / 波动过大）

[8] 结果处置
     ├─ 导出 CSV / Excel
     └─ 自动存档到「历史记录」

[9] 历史记录
     列表查看 → 点入详情看曲线对比 → 支持两个任务曲线叠加对比 → 可再次导出
     ✗ 分支：删除历史记录 → 二次确认后软删除
```

### 2.2 关键分支场景清单

| 编号 | 场景 | 触发条件 | 系统行为 | 归属阶段 |
|---|---|---|---|---|
| B1 | 文件格式不支持 | 上传非 CSV / 超过大小上限 | 前端即时拦截并提示 | P1 |
| B2 | 必需字段缺失 | 缺少商品/仓库/日期/销量任一列 | 拒绝入库，返回缺列名 + 标准模板下载链接 | P1 |
| B3 | 日期格式混乱 | 无法统一解析 | 提示支持的格式（YYYY-MM-DD 优先），拒绝入库 | P1 |
| B4 | 时间序列断档 | 日期不连续 | 提示断档区间，提供"自动插值 / 放弃"二选一 | P1 |
| B5 | 数据量不足 | 有效历史 < 窗口长度 × 2 | 拒绝执行，提示最少需要的天数 | P1 |
| B6 | 📌 序列数超上限 | 待预测序列数 > 上限（建议 1000） | 提示需筛选商品后重试，不启动流水线 | P1 |
| B7 | 📌 总耗时超限 | 端到端超过 1 分钟 | 软失败：返回"数据量过大"提示 + 已完成序列数，不给 502 | P1 |
| B8 | 📌 序列历史稀疏 | 该组合有效点数 < 90 | 三级分级：L2 降级到商品级分摊 / L3 标记不可预测 | P1 |
| B9 | 预测误差超标 | 加权 MAPE > 20% | 结果页显著标注，提示原因与免责声明 | P1 |
| B10 | 📌 长尾/新品序列 | 序列几乎全为零 / 极稀疏 | 走移动平均规则兜底，标注"低置信度" | P1 |
| B11 | 并发任务冲突 | 同一用户同时提交多个任务 | 队列串行执行，前端显示排队位置 | P2 |
| B12 | 会话过期 | Token 失效 | 返回 401 → 前端跳登录并保留草稿参数 | P1 |
| B13 | 大促异常冲击 | 序列出现极端尖峰 | 在结果页标注"该时段为异常区间，预测参考性下降" | P2 |
| B14 | 📌 图显存不足 | GPU OOM（2GB 显存被其他程序占用） | 自动回退到 CPU 推理，功能不中断 | P1 |

### 2.3 任务状态机（后端核心对象）

📌 因取消"即时训练"，不存在需要长时间排队的任务，状态机已简化（去掉 `queued`）：

```
created（已创建，参数待校验）
   │ 校验通过
   ▼
running（运行中，📌 目标 ≤ 1 分钟）
   ├─ 成功 ──→ succeeded（已成功）──→ 前端可看结果、可导出
   └─ 异常 ──→ failed（已失败）────→ 记录 error_code + error_msg，允许重试
                                          ├─ E_TIMEOUT：超 1 分钟
                                          ├─ E_TOO_MANY_SERIES：序列数超上限
                                          └─ E_INFER_FAIL：推理异常
```

⚠️ 需确认：任务失败后是否允许"原参数一键重试"，还是必须重新走一遍参数页？建议**允许一键重试**，降低用户挫败感。

## 第三章 功能模块清单与优先级

### 3.1 优先级定义

| 级别 | 含义 | 判定标准 |
|---|---|---|
| P0 | MVP 必备 | 缺失则主流程跑不通，或直接违背任务书硬性目标 |
| P1 | MVP 必备 | 主流程可跑通，但会显著影响可用性 / 数据正确性 |
| P2 | 二期迭代 | 提升体验或扩展场景，MVP 可用人工替代 |
| P3 | 远期规划 | 明确不在本期承诺范围 |

### 4.2 分层职责边界（明确"谁不能干什么"）

| 层 | 负责 | 明确不负责 | 边界依据 |
|---|---|---|---|
| 前端 | 展示、交互、请求编排、图表渲染 | 不做指标计算、不做数据清洗、不保存明文密码 | 避免前后端算法不一致导致结果对不上 |
| 接口子层 | 路由、参数 schema 校验、鉴权、序列化 | 不写业务规则（如"MAPE 超标要警告"） | 校验格式，不校验业务 |
| 业务编排层 | 流程串联、状态流转、异常归类、权限判定 | 不做矩阵运算 | 保持编排逻辑可读可测 |
| 算法服务层 | 清洗、特征、序列分级、基线、推理、指标计算 | 📌 **在线不做训练**；不碰 HTTP、不碰数据库 | **可脱离 Web 单独跑通**，这是可测性的前提 |
| 数据访问层 | CRUD、事务、连接管理 | 不做业务判断 | 防 SQL 渗透到上层 |
| 数据层 | 持久化 | —— | SQLite 单文件，⚠️ 见 6.3 风险 R4 |

> **架构红线 1**：算法服务层必须提供纯函数式入口（输入 DataFrame、输出预测结果与指标），使其能用一个脚本零 Web 依赖地跑完评估，这是保证"加权 MAPE ≤ 20%"这一硬指标可独立复现的关键。
>
> 📌 **架构红线 2**：**在线链路与离线训练必须共用同一份算法代码**（`algo/` 目录）。离线训练脚本从 `algo/` 导入，在线服务也从 `algo/` 导入，唯一差别是"模型从哪来"。这样可避免"训练时的预处理"与"推理时的预处理"不一致——这是时序项目最常见的隐藏 bug。

### 4.4 后端模块划分建议

```
app/
├── api/            # 路由层：auth / upload / predict / history
├── core/           # 配置、安全（哈希、Token）、异常定义
├── models/         # ORM 实体
├── schemas/        # Pydantic 请求/响应模型
├── services/       # 业务编排：task_service、predict_service
├── algo/           # 🔑 算法层（无 Web 依赖，在线离线共用同一份代码）
│   ├── preprocess.py     # 插值、异常截断
│   ├── features.py       # 滑动窗口、时间/滞后/滚动特征
│   ├── classify.py       # 📌 序列分级 L1/L2/L3（按有效历史长度 + 稀疏度）
│   ├── model.py          # LSTM 定义（含设备自动回退）
│   ├── train.py          # 📌 仅离线调用：训练 + 早停 + 网格搜索；服务进程不导入
│   ├── infer.py          # 📌 在线主路径：加载已注册权重 + 批量推理
│   ├── fallback.py       # 📌 L2/L3 规则兜底（同期均值 / 全局均值）
│   └── metrics.py        # 📌 加权 MAE/RMSE/MAPE + 基线 + 达标序列占比
├── dao/            # 数据访问
└── main.py

scripts/            # 📌 离线侧（不参与服务启动）
├── train_and_register.py  # 训练 → 评估 → 写 model_registry → 落盘权重
└── eval_report.py         # 零 Web 依赖跑通"加权 MAPE ≤ 20%"验收脚本
```

| 关键约束 | 说明 |
|---|---|
| `algo/` 不得 import `fastapi` / `sqlalchemy` | 保证可被离线脚本直接复用（架构红线 1） |
| `train.py` 不被 `services/` 引用 | 服务进程内存里不应存在训练相关依赖与图构建逻辑 |
| `classify.py` 的输出是**后续所有环节的输入** | 分级结果决定走推理还是走兜底，也决定指标的统计口径 |
| `metrics.py` 只认"预测值 + 真值 + 分级标签" | 不关心数据从哪来，因此在线与离线评估可用同一实现 |

⚠️ 需确认：任务书任务分解表第 6 项同时写了"Flask/FastAPI"，而第 3.2 技术选型表确定是 FastAPI。**以 FastAPI 为准**，Flask 属历史残留表述，建议在项目文档中明确统一，避免开发时产生分歧。

## 第五章 关键数据流与核心数据模型

### 5.1 关键数据流

#### 数据流 1：上传与校验流

```
用户选择 CSV
  → 前端：扩展名/大小预检（即时失败，不占带宽）
  → POST /api/v1/datasets（multipart）
  → 接口层：schema 校验
  → 业务层：调用 algo.preprocess.validate()
       校验列名 → 校验日期可解析 → 校验时间连续性 → 校验数值合法性
  → 通过：落盘 raw 文件 + 写 datasets 记录 + 返回 dataset_id 与预览数据
  → 失败：返回结构化错误（错误类型 + 定位 + 修复建议），不落盘
```

#### 数据流 2：预测任务流（核心链路，📌 在线同步 ≤ 1 分钟）

```
POST /api/v1/predictions  { dataset_id, granularity, horizon, features }
  → 接口层：schema 校验 + 序列数预检（估算序列数 > 上限则直接拒绝 E_TOO_MANY_SERIES）
  → 创建 task（status=running）→ 同步执行（总预算 60s，📌 不做排队）
  → algo 流水线（各步骤均带耗时埋点，落 task.duration_ms）：
       read raw CSV（已验证过，跳过重复校验）
         → 插值填补 → 异常截断
         → 【序列分级 classify.py】按有效历史长度 + 稀疏度打 L1/L2/L3 标签
         → 按分级分流：
              L1（历史充足）→ 逐序列归一化 → 滑动窗口 + 特征 → 批量推理
              L2（历史偏短）→ 规则兜底（同期均值 / 简单外推）
              L3（无有效历史）→ 全局均值兜底
         → 计算移动平均基线（同一测试段、同一序列集合）
         → 加权指标 + 逐序列 MAPE + 达标序列占比 + L1/L2/L3 覆盖计数
  → 结果写入 predictions（逐条预测值 + granularity_level）+ metrics（任务级）
  → task.status = succeeded，返回 task_id 与完整结果
  → 前端直接渲染（无轮询）
  → 超预算：task.status = failed，error_code = E_TIMEOUT，返回已完成阶段与建议（见 2.2 B7）
```

> 📌 **与 V1.0 的关键差异**：V1.0 写的是"创建 task → 排队 → 调度器 → 训练 LSTM → 轮询"。
> 经实测与决策（附录 C-3 + 附录 D），**1 分钟 SLA 物理上排除了在线训练**，因此改为
> "同步执行 + 预训练权重推理"。轮询逻辑保留在接口层（用于将来任务变重时平滑演进），
> 但当前实现路径不触发排队态。

> 📌 **为什么必须"同一序列集合"算基线**：如果基线在全量序列上算、模型只在 L1 上算，
> 提升幅度会被系统性放大，属于典型的偷换统计口径。基线必须与模型**同范围、同测试段**。

#### 数据流 3：结果导出流

```
GET /api/v1/predictions/{task_id}/export?format=csv
  → 业务层校验 task 归属（只能导出自己的）
  → 组装 DataFrame（商品, 仓库, 日期, 预测销量, 实际值(如有), 误差）
  → 生成导出文件到磁盘 → 返回下载流
  → 同时写 exports 记录（用于数据清理策略）
```

#### 数据流 4：历史回溯流

```
GET /api/v1/history?page=&size=
  → 按 user_id 过滤 → 按创建时间倒序 → 返回任务摘要列表
GET /api/v1/history/{task_id}
  → 校验归属 → 返回该任务完整结果（曲线点 + 指标）
```

### 6.3 主要技术风险与应对

| 编号 | 风险 | 影响 | 概率 | 应对思路 |
|---|---|---|---|---|
| R1 | **加权 MAPE ≤ 20% 的目标可能达不到** | 🔒 直接违反硬指标，影响答辩 | 中高 | ① 先跑通移动平均基线，量化差距；② 主指标按销量加权，长尾稀疏序列用规则兜底并单列统计；③ 📌 口径已定为"加权 MAPE 为主 + 达标序列占比为辅"（附录 C-1），不再存在口径歧义；④ 分 L1/L2 分别统计，不混算 |

## 附录 B：术语表

| 术语 | 含义 |
|---|---|
| SKU | 最小库存单位，即具体商品规格 |
| MAPE | 平均绝对百分比误差，越低越好，本项目硬指标 ≤ 20% |
| WAPE / 加权 MAPE | 按真实销量加权的 MAPE，= Σ\|y-ŷ\| / Σ\|y\|，本项目的**主判定口径** |
| MAE | 平均绝对误差 |
| RMSE | 均方根误差，对大误差更敏感 |
| 滑动窗口 | 用连续 N 天数据预测后续值，把时序样本化的方法 |
| 多步预测 | 一次预测未来多个时间点的值 |
| 移动平均基线 | 用近期均值外推的朴素方法，作为"模型是否真的有用"的对照，同时兼任长尾兜底模型 |
| 数据泄漏 | 训练时使用了未来信息，导致指标虚高、上线失效 |
| 早停 | 验证集误差不再下降时提前结束训练，防过拟合 |
| L1 / L2 / L3 | 序列三级分级：仓库×商品建模 / 降级到商品级 / 标记不可预测 |
| 达标序列占比 | 逐序列 MAPE ≤ 20% 的序列数占参与评估序列总数的比例 |
| 预训练推理 | 加载离线训练好的模型直接推理，不在请求内训练 |

## 附录 C：已确认决策记录

本附录记录项目负责人对关键问题的确认结论，作为开发依据；与正文冲突时以本附录为准。

### C-1 指标统计口径（对应 Q2）

**问题**：任务书给出「MAPE ≤ 20%、MAE/RMSE 相对基线降低 15%」两个硬指标，但未定义统计口径。

**确认结论**：

| 项 | 定义 |
|---|---|
| 基线方法 | **移动平均**（已确认） |
| 主判定口径 | **销量加权 MAPE**（即 WAPE）= Σ\|yᵢ-ŷᵢ\| / Σ\|yᵢ\| |
| 辅助口径 | **达标序列占比** = 逐序列 MAPE ≤ 20% 的序列数 / 参与评估序列总数 |
| 硬指标判定 | 加权 MAPE ≤ 20% **且** 加权 MAE/RMSE 相对基线降低 ≥ 15% |
| 口径一致性要求 | 基线的 MAE/RMSE 必须与主模型使用**同一批预测点、同一权重**计算 |

**为什么选加权口径**：长尾低销量序列的逐序列 MAPE 可达百分之几百，若用算术平均会把整体指标拉爆且没有业务含义；加权口径对应"整体的货量预测误差"，有明确的业务解释，且天然规避零销量除零问题。

**必须披露**：评估前提需注明"使用预训练模型、未针对输入数据微调"，写入 `metrics.eval_note`。

### C-2 预测粒度（对应 Q3）

**问题**：任务书 2.2-3 说"商品销量"，1.1/2.1 又强调"分仓规划"，两处不一致。

**联网查证的数据集事实**（来源：菜鸟-需求预测与分仓规划赛题公开资料及参考实现）：

| 事实 | 数值 |
|---|---|
| 商品数 | 963 |
| 分仓数 | 5（另有全国口径） |
| 数据时间范围 | 约 450 天 |
| 理论最大序列数 | 963 × 5 = 4,815 |
| 分布特征 | 长尾；大量商品"有段时间有销量、有段时间完全无数据"；分仓样本缺失 17,063 条 |

**确认结论**：

| 项 | 决策 |
|---|---|
| 仓库列 | **必需字段**（数据集必含），缺失即拒绝上传 |
| 主粒度 | **仓库 × 商品**（服务任务书的"分仓规划"卖点） |
| 降级策略 | **三级分级**：L1（有效点数 ≥ 90）/ L2（商品级聚合 ≥ 90 点，按历史占比分摊）/ L3（标记不可预测） |
| 归一化 | **按序列独立**，不做全局归一化 |
| 是否建 warehouses 表 | **不建**，MVP 阶段仓库仅作分组键 |
| 覆盖率披露 | L1/L2/L3 序列数与占比必须在结果页展示 |

**为什么这样定**：菜鸟数据集的核心价值就在分仓维度，若先聚合到商品级会不可逆地丢失信息；但 4,815 条序列中大量样本量不足，全量按仓建模既不可靠也无必要，故需分级而非一刀切。

### C-3 训练时机（对应 Q6）

**问题**：用户上传数据后，是即时训练模型，还是用预训练模型推理？

**关键约束**：**端到端等待时间上限为 1 分钟**（已确认，且为硬约束）。

**确认结论**：

| 项 | 决策 |
|---|---|
| 在线路径 | **纯预训练推理**，不训练 |
| 是否提供"重新训练" | **不提供**（1 分钟约束下物理不可行，已写入 1.4 不做清单） |
| 字段结构一致性 | **已确认一致** —— 预训练模型可直接套用，无需字段映射层 |
| 任务状态机 | 简化：去掉 `queued`（无长任务需排队） |
| 模型版本 | `tasks.model_version` 变为 **NOT NULL** |
| 1 分钟预算分配 | 读取校验 ≤10s / 预处理 ≤10s / 特征 ≤15s / 推理 ≤15s / 指标 ≤5s / 落库返回 ≤5s |

**为什么不可行即时训练**：单次 LSTM 训练（含早停与调参）耗时以分钟计，即便优化到极限也无法稳定在 1 分钟内；而在 1 分钟约束下，预训练推理的耗时是秒级，二者不在同一量级。

**与任务书的一致性**：任务书 3.3 原文为"将训练好的模型部署到服务端，通过 API 接口提供销量预测服务"——**本就指向预训练推理**，故本决策不是妥协，而是回归任务书原意。

| 环节 | 实测耗时 |
|---|---|
| 读取 CSV | 0.43 s |
| groupby 分组（4,815 序列） | 0.10 s |
| 排序 + 日期解析 | 0.36 s |

| 滚动均值 | 1.35 s |

### D-3 模型训练耗时（LSTM：hidden=32, layers=1, window=14）

| 样本量 | CPU | GPU(MX450) | GPU 加速比 | GPU 峰值显存 |
|---|---|---|---|---|
| 4,096 | 0.39 s | 0.32 s | 1.19× | 33 MB |
| 20,000 | 1.58 s | 0.91 s | 1.73× | 46 MB |
| 50,000 | 3.20 s | 1.13 s | 2.82× | 70 MB |
| 100,000 | 3.67 s | 0.84 s | **4.35×** | 111 MB |

**关键结论**：

1. **2 GB 显存完全够用** —— 10 万样本峰值仅占 111 MB（模型仅 5,454 参数）。原先"显存不足"的担忧不成立。
2. **数据量越大，GPU 优势越明显** —— 小数据量时存在固定启动开销，4 万样本以上才明显拉开差距。
3. **绝对耗时都很短** —— 即使纯 CPU 跑 10 万样本 3 个 epoch 也只需 3.67 秒。

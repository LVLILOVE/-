### 环节 ③ 结果解读（2:00 – 4:00）—— 这是重点

**动作**：滚动到结论条与四张指标卡

> 🎤「先看结论：本次预测 **加权 MAPE 13.1%**，低于任务书要求的 20%。」
>
> 🎤「但这一个数字不够。我们同时对比了**移动平均基线**，请重点看这一列：」

**动作**：指指标卡与基线对比表

| 指标 | 本项目 | 移动平均基线 | 任务书要求 | 结果 |
|---|---|---|---|---|
| **加权 MAPE** | **13.1%**（h=7） | —— | ≤ 20% | ✅ |
| MAE | 优于基线 | 基线 | 降低 ≥ 15% | ✅ |
| RMSE | 优于基线 | 基线 | 降低 ≥ 15% | ✅ |
| **达标序列占比** | 88.9%（8/9） | —— | ≥ 60% | ✅ |

> 📌 **口径必须讲清楚**（评委必问）：
> ① 主指标是**销量加权 MAPE**（`Σ|e| / Σ|y|`），不是「每个序列 MAPE 再取平均」——
> 后者会让一条日销 3 件的小序列和一条日销 300 件的大序列权重相同。
> ② **基线必须在完全相同的预测点、相同序列集合上计算**，否则就是在比两个不同的题。
> ③ 预训练模型的整体评估（113 序列）为 **MAPE 14.26% / MAE↓26.4% / RMSE↓27.5% / 达标 84.0%**，
> 本次演示是小样本（9 序列）所以数字略有差异，**方向一致**。

**动作**：滚动到覆盖率面板

**预期画面**：`L1 = 8 / L2 = 1 / L3 = 0`，合计 9

> 🎤「这一块是我们在数据处理上花时间最多的地方。数据集是**长尾**的：
> 天池菜鸟数据集 963 个商品 × 5 个仓，理论上有 4,815 条序列，
> 但真实只有其中一部分 —— 有 **17,063 条仓库缺失样本**，很多商品只在 1–2 个仓有货。
>
> 所以我们设计了**三级降级**：
> · **L1** 本仓历史 ≥ 90 天 → 走 LSTM 推理；
> · **L2** 本仓不够，但**同商品跨仓聚合** ≥ 90 天 → 商品级降级 + 按历史占比分摊；
> · **L3** 跨仓聚合仍不够 → **不输出数值预测**，只给历史均值。」
>
> 🎤「本次数据里 `item_1008 / 广州仓` 只有 45 天，本仓不足 90 天，
> 但加上同商品上海仓的 273 天，聚合 318 天 ≥ 90 —— 所以它走了 **L2**，
> 这是**正常路径，不是异常分支**。真正的异常是"数据不够还硬给一个数"。」

**动作**：指出折线图中的 618 尖峰（`item_1001 / 上海仓`）

> 🎤「看这条线：6 月 18 日前后有明显的大促尖峰，预测曲线能**跟随**这个形态。
> 这里有一个反直觉的处理 —— 我们对异常尖峰做截断，但**大促期间刻意不截断**。
> 因为尖峰是噪声，而**大促是唯一可学的业务信号**，无条件削平等于把模型最该学的部分删了。」

**动作**：滚动到明细表 → 翻到第 2 页 → 点「导出 CSV」→ 用 Excel 打开

> 🎤「明细支持服务端分页，本次共 **63 行**（9 序列 × 7 天）。
> 导出是带 BOM 的 UTF-8，Excel 打开中文不乱码 —— 这看起来是小事，
> 但不加 BOM 的 CSV 在中文 Windows 上打开必乱码。」

## 3. 备用问答（评委高频追问）

| 追问 | 回答要点 |
|---|---|
| **为什么用 LSTM 而不是 XGBoost / Prophet？** | 任务书 §3.2 指定 LSTM；且本任务是多步序列预测 + 促销冲击，LSTM 能直接刻画趋势/周期/冲击的耦合。同时我们保留移动平均作为基线，用**相对提升**说话，而不是宣称"LSTM 一定更好"。 |
| **为什么只预测 7–30 天？** | 误差随步长单调增长（`6.3` 局限性条款）。30 天是补货决策的有效期上限，再长预测意义不大。 |
| **2GB 显存够吗？** | 够。模型 31,729 参数、hidden=48、2 层，⏱️ 训练时峰值显存仅 **111 MB**。无 GPU 时自动回退 CPU（⏱️ 端到端 23.5 s，仍在 60 s 内）。 |
| **为什么不做在线重训练？** | ① 端到端 60 s 预算装不下「训练+调参+早停」；② 单机 SQLite + 内存限流，多用户并发训练会互相抢占。故采用**预训练推理**，并把这个限制**明确写在界面上**（参数页高级设置）。 |
| **"两套数字"问题怎么防？** | 首页硬指标**构建期从 `outputs/eval_report.json` 注入**，禁止手写（`QD-06`）；并有一条纪律 `GIT-7`：改算法参数后必须重跑训练与评估，且有断言守卫生成物与算法产物一致。 |
| **数据安全怎么做的？** | ① 密码 bcrypt 哈希（含 72 字节边界处理）；② JWT 带 `token_version`，改密/重置密码后旧 Token **立即失效**；③ 数据隔离：所有业务查询强制带 `user_id` 过滤，**唯一例外**是管理端，且限定在单文件并全操作审计；④ 生产要求 HTTPS。 |
| **覆盖率里的 L2、L3 会不会拉低指标？** | 会，所以**主指标只统计 L1**。L2 是规则兜底（实测 MAPE 约 60%），把 L2 混进主指标会把 13.6% 变成 25.9%，那是自欺。我们选择如实分开披露。 |
| **测试做了多少？** | 35+ 套可复现断言脚本：算法自检 69 项、静态/接口/浏览器分层、边界 25 条（B-01~B-25）、性能 7 项、契约双向比对、无障碍 53 项（FAIL 0）。全部**实跑**过，不是代码审查。 |

## 4. 故障预案（现场出了意外怎么办）

| 意外 | 应对 |
|---|---|
| 后端起不来 | 检查 `.env` 是否有 `JWT_SECRET`（≥ 32 字符）→ 这是 `BE-05` 的预期保护，不是 bug |
| 页面全白 | 看浏览器是否走了系统代理（`HTTP_PROXY`）→ 用 `--no-proxy-server` 或清代理 |
| `/docs` 打不开 | 直接用离线归档件 `outputs/电商销量预测系统_API接口文档_V1.0.html`（双击可开，零外链） |
| 网络完全不可用 | 全部素材已离线：前端本地、接口文档离线、演示数据本地。**不需要联网** |
| 上传一直失败 | 改用 `outputs/models/demo_sales.csv`（内置示例）点「一键加载示例数据」 |
| 预测任务超时 | 改小步长（7 天）或减少序列；实在不行直接取历史记录里的既有任务演示结果页 |
| 时间不够 | **砍环节 ④（失败分支）之外的都别砍** —— 失败分支是 `DOD-EP10` 的硬要求；可压缩的是环节 ③ 的图表细讲 |
| 忘登录导致导出 401 | 这就是「演示必须登录」的原因（已写进检查清单第 3 项）。现场立刻登录即可，不影响已生成的任务 |

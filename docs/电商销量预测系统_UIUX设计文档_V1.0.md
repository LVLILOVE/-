## 1. 概述与设计原则

### 1.1 设计要解决的核心矛盾

这个产品的用户不是数据分析师。用户画像（PRD §2.1）显示，主用户是**熟练使用 Excel 但不懂编程的运营/补货专员**，其技术能力上限是"会筛选、会排序、会拖拽"。而系统内核却是一套**多层级 LSTM 时序模型 + 三级序列降级机制**。

于是设计面对的核心矛盾是：

> **如何在不让用户理解"LSTM""加权 MAPE""序列分级"的前提下，让用户信任并使用一个依赖这些概念才能正确解读的结果？**

设计给出的答案不是"隐藏复杂性"，而是**分层暴露**：

| 层级 | 面向谁 | 暴露什么 | 设计手段 |
|---|---|---|---|
| L1 结论层 | 所有人（含老板 `PER-C`） | 达标 / 未达标、能不能用 | 判定结论条、四张指标卡 |
| L2 解释层 | 运营 `PER-A` | 误差多大、为什么、覆盖了多少 | 基线对照表、覆盖率面板、误差直方图 |
| L3 方法层 | 仓配 `PER-B`、答辩评审 | 用的什么模型、什么口径、有什么局限 | 模型适用性说明、技术参数表、免责声明 |

> `UX-GOAL-01`：任何页面都不得把"方法层"信息作为主干路径的必经步骤。用户走完主干只需读"结论层"。

### 1.2 设计目标与衡量方式

| 编号 | 设计目标 | 衡量方式（可证伪） |
|---|---|---|
| `UX-GOAL-02` | 零算法背景用户可独立跑通主干 | 首次使用完成率 ≥ 60%（PRD 成功指标）；默认参数即可提交（`NFR-USE-02`） |
| `UX-GOAL-03` | 错误"说人话" | 所有面向用户的错误提示含"错在哪 + 怎么改"（`NFR-USE-03`）；禁止裸错误码 |
| `UX-GOAL-04` | 结论可信且不误导 | 覆盖率如实披露（`FR-VIS-07`）；误差超标警告不可折叠（`FR-VIS-06`）；L3 不输出伪预测 |
| `UX-GOAL-05` | 视觉规范可机械验收 | 双主题对比度检查全通过（`UX-A11Y-*`）；令牌单一来源（`app.css`） |
| `UX-GOAL-06` | 界面语言面向业务而非工程 | 界面术语表（§11.2）中每个术语都有面向业务的中文解释 |

### 1.3 六条设计原则

以下六条是本项目所有界面决策的**仲裁依据**。当两条原则冲突时，编号小者优先。

**原则一 · 结论先于过程（`UX-GOAL-07`）**
每个页面第一屏必须回答"我现在该关心什么"。结果页第一张卡是"是否达标"，不是曲线图；工作台第一屏是"最近任务"，不是功能菜单。

**原则二 · 不确定必须显式标注（`UX-GOAL-08`）**
把不确定的东西说成确定，比不给结论更危险。因此：L3 序列的预测列显示"—"而非历史均值；L2 降级序列带"中"置信度标签；超标结果页顶部常驻红色警告。

**原则三 · 错误即教程（`UX-GOAL-09`）**
每一次校验失败都是一个教学机会。上传错误不只说"缺列"，而是画出"已识别表头"徽标组 + 高亮缺失列 + 给出修正路径 + 提供模板下载。

**原则四 · 默认值可用（`UX-GOAL-10`）**
用户不修改任何参数即可得到有效结果。粒度固定不可改（`📌` 决策），步长默认 7 天，节假日特征默认开启，高级设置折叠。

**原则五 · 深浅双主题对等（`UX-GOAL-11`）**
深色为默认主题（与开发环境一致）。任何颜色不得硬编码十六进制值，必须经令牌；同一套令牌在两种主题下都必须通过 WCAG AA。

**原则六 · 演示与产品分离（`UX-GOAL-12`）**
原型中的"演示状态"药丸、"原型说明"蓝色块、"差异标注"黄色块均**不属于产品界面**，交付实现时移除。产品界面只保留页脚免责声明（那是真实需求）。

### 1.4 设计不做的事（范围红线）

| 不做的事 | 理由 |
|---|---|
| ❌ 为迎合视觉而引入大数据看板式密集图表 | 用户是运营不是分析师，图表数量与认知负担须克制 |
| ❌ 把"模型训练"做成可交互流程 | 训练时机已 `📌` 确定为纯预训练推理 |
| ❌ 用颜色作为唯一的信息载体 | 无障碍要求（`UX-A11Y-05`）：颜色须配文字/图标 |
| ❌ 在界面上出现概率值、置信区间的精确数值 | 置信区间为 P2 功能，本期仅演示其视觉形态，不承诺数值准确性 |
| ❌ 多语言 / 多时区切换控件 | 本期仅简体中文、本地时区（`NFR-COMP-04` / `Q8`） |

## 2. 用户与场景映射

### 2.1 三类用户的设计诉求

| 维度 | `PER-A` 运营/补货专员 | `PER-B` 仓储/分仓规划 | `PER-C` 中小商家老板 |
|---|---|---|---|
| 与界面的关系 | **主用户**：完成上传→参数→结果全流程 | **次主用户**：重点用分仓对比与覆盖度 | 只看结论 |
| 屏幕 | 办公笔记本 1366×768 ~ 1920×1080 | 办公台式机 | 手机 / 平板（只读结果页） |
| 耐心阈值 | 中（每周固定使用一次） | 低（大促前集中使用，要快） | 极低（1 分钟内要有结论） |
| 最怕的体验 | 上传失败却不说清哪列有问题 | 看不懂"哪个仓该多备" | 一屏都是看不懂的数字 |
| 设计侧重 | 上传错误的可读性、参数页的确定性 | 分仓曲线对比、L1/L2/L3 占比 | 判定结论条、指标卡、单条曲线 |

> `UX-GOAL-13`：对 `PER-C` 的适配采用**渐进披露**而非单独做简版页面——结果页顶部三张卡（判定/指标/覆盖度）即为简版视图，向下滚动才进入明细。这样避免维护两套界面。

### 2.2 九个用户故事 → 界面承载

| 编号 | 用户故事（PRD §2.2） | 承载页面 | 关键设计手段 |
|---|---|---|---|
| `US-01` | 上传本周销量表拿未来 7 天分仓预测 | upload → params → running → result | 五步流程条常驻；默认参数可直提 |
| `US-02` | 误差偏高时被明确告知 | result | 顶部判定条转"未达标"；红色警告条不可折叠（`FR-VIS-06`） |
| `US-03` | 导出 Excel 发采购同事 | result / history-detail | 导出按钮置于页头，列顺序固定（`FR-VIS-05`） |
| `US-04` | 按仓库维度对比预测曲线 | result（按仓库对比）/ compare | 序列切换三模式：单序列 / 多序列叠加 / 按仓库对比 |
| `US-05` | 知道哪些商品数据太少无法预测 | result 覆盖率面板 | L1/L2/L3 条形 + 计数 + 占比 + 文字解释 |
| `US-06` | 回看上月预测的实际表现 | history → history-detail | 参数快照冻结；指标与覆盖率原样复现 |
| `US-07` | 老板只想看汇总指标和一条曲线 | result（首屏） | 判定条 + 指标卡 + 默认选中一条 L1 序列 |
| `US-08` | 新手一键加载示例数据看效果 | upload / dashboard | "改用示例数据"按钮 + 工作台"用示例数据体验"入口 |
| `US-09` | 出错时看到"错在哪、怎么改" | upload（全类错误）/ running（失败态） | 结构化错误卡片 + 修正建议 + 错误明细下载 |

## 3. 视觉设计语言

### 3.1 设计理念

视觉语言参考了**阿里云天池数据集页的信息架构**（左主内容 + 右元信息栏、字段说明表格、标签页切换），视觉风格对齐**现代 SaaS 数据产品**：克制、留白充分、信息密度适中、以中性色为主、以单一品牌色做强调。

三条视觉主张：

1. **青蓝而非 bootstrap 蓝**——品牌色相 `205`（青蓝），刻意避开 `--bs-primary: #0d6efd` 一类陈旧蓝，避免"套模板"观感。`UX-COL-01`
2. **深色优先**——默认深色（`html.dark`），与开发者日常环境一致；浅色为可选。`UX-COL-02`
3. **色不过三**——单屏内语义色（成功/警告/危险/信息）通常只出现 1–2 种，避免"彩虹看板"。`UX-COL-03`

### 3.2 色彩系统

#### 3.2.1 色彩空间

全部颜色以 **`oklch()`** 定义。选它的理由：

| 优势 | 对本项目的意义 |
|---|---|
| 感知均匀 | 调 L 值时明度变化线性，便于按 WCAG 反解目标亮度 |
| 色相独立 | 品牌色相 `--brand-h: 205` 抽为变量，换品牌色只改一处 |
| 支持 alpha 语法 | `oklch(L C h / 0.12)` 直接表达半透明浅底（`-soft` 令牌） |

> `UX-COL-04`：**禁止**在组件层硬编码 `#rrggbb` / `rgb()` / `hsl()`。所有颜色必须引用 `:root` 或 `html.dark` 中的令牌。原型中仅剩的硬编码值集中在三处装饰性渐变（品牌 mark、进度条、认证页光晕），已列入 `UX-GOV-03` 治理清单。

#### 3.2.2 品牌色与语义色（修复后取值）

**浅色主题（`:root`）**

| 令牌 | 取值 | 用途 | 对比度（实测 ⏱️） |
|---|---|---|---|
| `--primary` | `oklch(0.475 0.145 205)` | 主色：按钮填充、链接、激活态 | 白字于其上 **4.68:1** ✓ |
| `--primary-hover` | `oklch(0.41 0.15 205)` | 主按钮悬停 | — |
| `--primary-soft` | `oklch(0.475 0.145 205 / 0.12)` | 主色浅底（选中项、标签底） | 主色文字于其上 **4.55:1** ✓ |
| `--primary-ring` | `oklch(0.475 0.145 205 / 0.35)` | 焦点环 | 非文字，豁免 |
| `--success` | `oklch(0.51 0.15 155)` | 成功/达标 | 白字于其上 **4.72:1** ✓ |

#### 3.2.3 on-color 令牌组（本次无障碍修复的核心）

**问题**：浅色主题下，主色是深色，其上油墨应为白色；深色主题下主色是亮色，其上油墨应为深色。若在组件里写死 `color: #fff`，则在深色主题的亮色填充上必然失守——实测"白字于 success"仅 **2.71:1**（需 4.5:1）。

**解法**：引入独立的 on-color 令牌组，使"填充色"与"其上油墨"解耦：

| 令牌 | 浅色 | 深色 | 语义 |
|---|---|---|---|
| `--on-primary` | `oklch(0.99 0 0)` | `oklch(0.19 0.03 205)` | 主色填充上的前景 |
| `--on-success` | `oklch(0.99 0 0)` | `oklch(0.19 0.03 155)` | 成功色填充上的前景 |
| `--on-danger` | `oklch(0.99 0 0)` | `oklch(0.19 0.03 25)` | 危险色填充上的前景 |

> `UX-COL-05`：**凡置于实色填充之上的文字/图标，必须使用对应的 `--on-*` 令牌，禁止写死 `#fff`。** 原型中已完成 7 处替换（`.brand-mark`、`.btn-primary`、`.btn-danger`、`.side-item.active .badge-count`、`.stage.done/.fail .stage-icon`、`.verdict.pass/.fail .vd-icon`、`.state-pill.active`）。

- 无障碍：原生 `input` 保留语义，`focus-visible` 显示 3px 环

> `UX-CMP-05`：开关必须配可见文字标签（`.switch-text`），不得只有开关本体。原型中"启用节假日特征"、"记住我"、"我已阅读并同意"均遵循。

### 4.5 徽标与状态点

**徽标 `.badge`**（8 变体）

| 变体 | 语义 | 深色特殊处理 |
|---|---|---|
| `.badge-primary` | 主色标签 | — |
| `.badge-success` | 成功 / L1 / 达标 | 字色提亮 `oklch(0.80 0.15 155)` |
| `.badge-warning` | 警告 / L2 | 字色提亮 `oklch(0.84 0.15 75)` |
| `.badge-danger` | 危险 / 失败 | 字色提亮 `oklch(0.76 0.18 25)` |
| `.badge-info` | 信息 | 字色提亮 `oklch(0.80 0.13 250)` |
| `.badge-neutral` | 中性 / L3 | — |

规格：`padding: 1px 7px`、`border-radius: 99px`、11px/600、圆角胶囊。
> `UX-A11Y-02`：深色主题下徽标文字必须**显式写回提亮值**（见 `html.dark .badge-*`）。若省略，会继承浅色主题压深后的值，导致暗底上文字发暗。

**状态点 `.dot`**：7px 圆点，4 色变体（success/warning/danger/info）+ neutral。`.dot-pulse` 用于运行态，1.6s 脉冲。

### 4.6 提示条 `.alert`

四种语义变体：`.alert-danger` / `.alert-warning` / `.alert-info` / `.alert-success`。
结构：`[图标] [.alert-body: .alert-title + 正文(可含 ul)]`。
`.alert-accent-danger` 附加左 4px 危险竖条（用于需要最高注意力的错误）。

> `UX-CMP-06`：提示条的**底色为 `-soft` 令牌，正文色为 `--text`**（可读性），仅图标使用语义实色。这样保证长文本可读性不受底色影响。

### 4.7 卡片 `.card`

### 4.9 指标卡 `.metric`

|---|---|---|
| 容器 | `.metric` | 底 `--surface`，框 `--border`，圆角 `--radius-sm` |
| 左侧色条 | `.metric::before` | 3px 宽竖条，色由 `--metric-accent` 决定 |

| 数值 | `.metric-value` | 24px/700，`tabular-nums`，`.unit` 单位 13px |

### 4.10 进度、时间轴与阶段列表

| 组件 | 类 | 规格 |
|---|---|---|
| 进度条 | `.progress` | 高 6px（`.thin` 4px），渐变填充 `--primary → oklch(0.66 0.16 265)` |

### 4.11 空状态与骨架屏

**空状态 `.empty`**：46px 圆形图标槽 + `<h4>` 标题 + 说明（`max-width: 46ch`）+ 主次操作按钮。
**骨架屏 `.skeleton`**：渐变微光动画；辅助类 `.sk-line.w40/.w60/.w80` 控制宽度。

横向标签，激活态下边框 2px `--primary` + 主色文字。`.tab-panel[hidden]` 隐藏非激活面板。
> `UX-CMP-12`：标签页仅用于**同层内容的视图切换**，不作为主流程步骤切换（主流程用步骤条）。

### 4.13 图表组件

原型图表为**自研轻量 SVG 库**（`assets/charts.js`，5 个函数）：`lineChart` / `multiLineChart` / `histChart` / `sparkline` / `miniBar`。所有图形使用语义 CSS 变量着色，随主题自动重绘。

| 函数 | 用途 | 关键规格 |
|---|---|---|
| `lineChart` | 历史实线 + 预测虚线 + 置信带 | 历史线 `--c1` 实线 2px；预测线 `--c3` 虚线 `6 4`；分界线标注"预测起点"；可选限值参考线（`--warning`） |
| `multiLineChart` | 跨任务/多序列对比 | 每序列独立色与虚实；图例自动生成 |
| `histChart` | 逐序列 MAPE 分布直方图 | 分箱 ≤ 20（默认 12）；超标箱用 `--danger` |
| `sparkline` | 表格内迷你走势 | 74×22px，正/负用 success/danger |
| `miniBar` | 覆盖率占比条 | 按 value 计算百分比宽度 |

> `UX-CMP-13`（🔒）：图表**不得以颜色作为唯一区分手段**——历史/预测除颜色外还需线型（实线/虚线）区分；直方图超标箱除颜色外需在图例中说明。
> `UX-CMP-14`：SVG 图表须带 `role="img"` + `aria-label` 描述（`lineChart`/`histChart` 已实现）；纯装饰性 `sparkline` 须 `aria-hidden="true"`。

### 4.14 覆盖率披露面板 `.cover-panel`

左：达标环 `.gauge`（`conic-gradient` 纯 CSS）+ 中心百分比 + 说明文字。
右：三段占比条 `.cover-bar` + 图例 `.cover-row`（色块 + 名称 + 计数 + 占比）+ L1/L2 分组 MAPE 小卡。

> `UX-CMP-15`（📌 `FR-VIS-07`）：覆盖率面板为**必展示项**。三项计数之和必须等于总序列数（可机械校验）。

### 4.15 判定结论条 `.verdict`

`.verdict.pass`（绿左条 + success-soft 底）/ `.verdict.fail`（红左条 + danger-soft 底）。
结构：`[32px 圆形图标] [.vd-t 标题 + .vd-d 说明] [右侧综合判定]`。

> `UX-CMP-16`：结论条置于结果页**第一张卡**，是 `UX-GOAL-07`（结论先于过程）的直接体现。

### 4.16 弹层与确认

**删除确认**（`history` 页）：不用浏览器原生 `confirm`，而用**页内卡片式确认**——列出将删除的任务行 + 复用危险提示条 + 要求**逐字输入任务 ID**才可提交。

> `UX-CMP-17`（高价值设计）：危险操作采用"输入 ID 确认"而非"点两次确认"，从根本上避免误触，尤其适合列表批量场景。文案强调"若只是不想在列表中看到，请使用筛选而非删除"（给出更优替代路径）。

## 5. 交互与状态规范

### 5.1 状态模型总览

PRD 要求界面覆盖"空状态、加载、异常等关键状态"（`AC-P3`）。本项目将状态归纳为 **5 类 × N 处**，全站统一：

| 状态类 | 定义 | 视觉手段 | 是否阻塞 |
|---|---|---|---|
| **空态** | 无数据 / 首次使用 | `.empty`（图标 + 标题 + 说明 + 主次按钮） | 否，给下一步 |
| **加载态** | 数据请求中 / 处理中 | `.skeleton` 骨架 / `.progress` 进度条 / `.dot-pulse` | 是（局部） |
| **正常态** | 有数据且校验通过 | 常规内容渲染 | 否 |
| **错误态** | 校验失败 / 任务失败 / 请求失败 | `.alert-danger` + 结构化定位信息 + 修正建议 | 是（需处置） |
| **边界态** | 超出阈值但未失败 | `.alert-warning` / `.badge-warning` + 说明 | 否，警示 |

> `UX-ST-01`：**任何"等待"都必须有视觉反馈**，且等待超过 1 秒的必须有进度或骨架，不得出现"点了没反应"。对应 `NFR-PERF-06`（首屏 ≤3s）与 `NFR-USE-03`（错误可读）。

### 5.2 空状态设计规范

| 处 | 触发 | 主操作 | 次操作 |
|---|---|---|---|
| 历史任务列表 | 用户无任何任务 | 上传数据开始预测 | 查看数据格式要求 |
| 结果页 | 任务失败/超时无结果 | 调整参数重跑 | 返回历史任务 |
| 对比页 | 选中 < 2 个任务 | 返回选择 | 查看全部历史任务 |
| 上传页 | 初始未选文件 | （拖拽区本身即空态） | 下载标准模板 / 改用示例数据 |

> `UX-ST-02`：空态文案必须**说明为什么空 + 给出下一步**，禁止只写"暂无数据"。

### 5.3 加载态设计规范

| 场景 | 手段 | 时长阈值 |
|---|---|---|
| 结果页首屏加载 | 骨架屏（标题行 + 图表块 + 4 张指标卡占位） | 立即显示，消除后替换 |
| 历史列表加载 | 骨架行（3 条） | 立即 |
| 文件上传 | 进度条 `.progress` + 百分比 | 上传即显 |
| 数据校验（7 步） | 进度条 + 当前步骤文字"第 N/7 步" | 立即 |
| 提交任务 | 提示条"正在提交任务…" + 进度条 | 立即 |
| 任务执行 | 五阶段列表 + 总进度 + 时间轴 + 实时日志 | 进入执行页即显 |
| 按钮提交中 | 按钮禁用 + 文案改"登录中…/提交中…" | 立即 |

> `UX-ST-03`：**骨架屏的形状必须与真实内容一致**（避免布局跳动 CLS）。结果页骨架的指标卡占位高度 78px 与真实 `.metric` 一致。
> `UX-ST-04`：加载态须防止重复提交——按钮进入 disabled 并变更文案，而非仅变灰。

### 5.4 错误状态设计规范（核心）

**结构化错误契约**（`FR-UPL-05`）：上传校验失败时，错误卡片必须包含五要素：

| 要素 | 说明 | 示例 |
|---|---|---|
| ① 错误码 | 右上角徽标 | `40001` |
| ② 一句话结论 | `.alert-title`，说人话 | 缺少必需字段：warehouse_id（仓库编码） |
| ③ 定位信息 | 失败步骤 / 行号 / 列名 | 校验顺序第 3 步失败 |
| ④ 可视化定位 | 已识别表头徽标组（✓绿 / ✗红）或错误明细表 | `✓sku_id ✓date ✓sales ✗warehouse_id（缺失）` |
| ⑤ 修正路径 | "如何修正"信息条 + 错误明细下载 | 请在表头补充「仓库编码」列后重新上传 |

**五类校验错误的差异化呈现：**

| 错误类 | 错误码 | 专属呈现 |
|---|---|---|
| 缺字段 | `40001` | 表头徽标组 + 修正建议 |
| 日期异常 | `40002` | 错误明细表（行号 + 原始值 + 期望格式） |
| 负值 | `40003` | 错误明细表 + 强调"不自动取绝对值" |
| 序列超限 | `40004` | 当前值 vs 上限对比卡 + 筛选建议 |
| 时间断档 | `40005` | 断档区间表 + **二选一处置**（自动插值 / 放弃上传） |

> `UX-ST-05`（🔒 `FR-UPL-13`）：断档类错误**必须由用户显式选择处置方式**，系统不得自动继续。文案明示"系统不会自动继续"。

**任务失败态**：`running` / `history-detail` 的失败卡需含：错误码（`E_TIMEOUT 50001` / `E_INFER_FAIL 50002`）、失败阶段、完成进度（如 42/50 条）、实际耗时 vs 上限、设备状态、"为什么失败"原因分析、处置建议（降步长/缩范围/查回退）、重跑入口。

> `UX-ST-06`（🔒 `NFR-REL-02`）：超时软失败**不得**呈现为原始 502/504。文案为业务语言："端到端耗时 61.2 秒，超过 60 秒硬上限，已完成 42/50 条序列"。

### 5.5 成功与确认反馈

| 场景 | 反馈 |
|---|---|
| 校验通过 | 卡片标题转绿 + 徽标"7/7 项检查全部通过" + 数据预览 + 下一步主按钮 |
| 任务完成 | 完成态卡：`verdict pass` + "端到端耗时 X 秒，满足 60 秒硬约束" + 序列分级小结 + 查看结果/返回历史 |
| 结果达标 | 顶部判定条 `pass` + 四项指标 + 基线对照表 |
| 结果超标 | 顶部判定条 + **不可折叠的红色警告**（`FR-VIS-06`） |
| 导出 | 触发下载（CSV 带 BOM，`NFR-COMP-05`） |
| 删除 | **页内二次确认**（输入任务 ID），非原生弹窗 |

> `UX-ST-07`（🔒 `FR-VIS-06`）：MAPE 超标的警告**不得可折叠、不得可关闭**，必须包含可能原因（数据量不足 / 波动过大 / 步长偏长）与建议动作。

### 5.6 键盘可达性与焦点

| 规范 | 要求 | 现状 |
|---|---|---|
| `UX-ST-08` | 所有可交互元素可由 Tab 到达 | 原生元素基本满足 |
| `UX-ST-09` | 焦点可见（`:focus-visible` 外环） | 按钮/输入/开关/单选卡均已实现 |
| `UX-ST-10` | 焦点顺序与视觉顺序一致 | 布局为线性流，一致 |
| `UX-ST-11` | 模态/确认层需焦点捕获与 Esc 关闭 | ⚠️ 原型为页内卡片式确认，未实现 Esc 关闭与焦点环，列 `UX-GOV-06` |
| `UX-ST-12` | 自定义 radio/switch 保留原生语义与键盘行为 | 已满足（隐藏原生 input，键盘仍可操作） |

### 5.7 表单校验时机

| 时机 | 规则 |
|---|---|
| 输入时 | 仅做**正向**实时反馈（如密码强度条满足项变绿），不提前报错 |
| 失焦时 | 可校验单字段格式（邮箱格式） |
| 提交时 | 全量校验；失败则高亮字段 `aria-invalid="true"` + 显示 `.field-error` |
| 服务端返回后 | 展示服务端结构化错误（如"邮箱已注册"） |

> `UX-ST-13`：**禁止在用户尚未输入时就标红**（如空表单首次进入即报"必填"）。原型登录/注册页均以"正常态"为默认，符合。

> 因此管理端**不是「另一套视觉语言」**，而是同一套后台里多出来的两个页面。
>
> 🔒 **`AD-P02` 的三类破坏性操作文案必须彼此区分**：
> - **停用账号**：可随时重新启用 → 文案写「可恢复」
> - **重置密码**：不可撤销，且该用户旧登录态立即失效 → 文案必须点明这点
> - **强制删除任务**：**硬删除不可恢复**，连带删`predictions` / `metrics`
>   → 文案写「**此操作不可恢复**」，并**明示与用户侧软删除不同**
>
> ⚠️ 最易犯的错是把管理侧文案沿用成用户侧那样。用户侧「删除历史」是**软删除**
> （数据仍可由管理员查回），所以那边写「可恢复」是对的；管理侧是**物理删除**。
> 沿用软删文案 = 欺骗用户，会让人事后才发现数据找不回来。

```css
@media (pointer: coarse) {
  .btn      { min-height: 44px; padding: .625rem 1rem; }
  .btn-sm   { min-height: 40px; }
  .input, .select { min-height: 44px; }
  .side-item{ min-height: 44px; }
  .state-pill, .tab { min-height: 40px; }
}
```

理由：桌面鼠标指针定位精度高，34–38px 更紧凑高效；触屏（`pointer: coarse`）才需要放大。**不要为了移动端把所有桌面按钮都撑到 44px**，那会破坏信息密度。

### 10.7 响应式断点

原型采用 5 档断点（含 900px 侧栏折叠、1100px 右栏下移、640px 单列）：

| 断点 | 触发变化 |
|---|---|
| ≤1180px | 隐藏页头品牌副标题（保导航单行） |
| ≤1100px | `.with-aside` 右栏下移并前置（`order: -1`） |
| ≤1080px | 工作台任务行隐藏"步长/序列数/趋势"列 |
| ≤900px | 侧栏转 fixed 抽屉（`.sidebar.open` 滑入）；网格 `grid-2/grid-3` 转单列；主内容 padding 收紧 |
| ≤640px | 页头主导航隐藏；`h1` 降至 1.375rem；三列单选卡转单列 |

> `UX-RSP-01`：**必须补齐 320px 断点**（无障碍与低端设备要求）。当前最窄适配至 640px，320–640px 区间未专门优化，列 `UX-GOV-08`。整改要点：`--maxw` 与内边距自适应、表格横向滚动（已有 `.table-wrap`）、拖拽区最小高度、按钮换行。
> `UX-RSP-02`（对齐 `NFR-COMP-02`）：1366×768 及以上为完整功能支持基线；手机端**仅需可查看结果页**，不要求完整操作。因此移动端优化重点在 `result.html`，其次是 `history.html`。

### 10.8 打印样式

`@media print` 隐藏页头、侧栏、演示状态栏、原型标注、页脚，主内容 padding 归零（`app.css` 第 22 章）。用途：用户直接打印或另存为 PDF 分享预测结果。

### 11.2 界面术语表（业务口径）

| 术语 | 界面用词 | 面向业务的解释（可作悬浮提示） |
|---|---|---|
| SKU | 商品 / 商品编码 | 具体商品规格 |
| warehouse | 仓库 / 分仓 | 发货仓，编码为字符串 `1`–`5` |
| 序列 | 序列（仓库 × 商品） | 一个商品在一个仓的历史销量走势，是本系统预测的最小单位 |
| MAPE / WAPE | 加权 MAPE | 整体货量的相对误差，越低越好；门槛 ≤ 20% |
| MAE / RMSE | 加权 MAE / RMSE | 绝对误差 / 大幅误差的敏感度指标 |
| baseline | 移动平均基线 | 用近期均值外推的朴素方法，用来证明"模型确实有用" |
| L1 / L2 / L3 | 分级：模型推理 / 商品级降级 / 不可预测 | 依据历史数据多少决定用模型还是用规则兜底 |

### 11.3 数字与单位格式

| 类型 | 格式 | 示例 |
|---|---|---|
| 千分位整数 | `toLocaleString('zh-CN')` | `14,305` |
| 百分比 | 保留 1 位小数 + `%` | `14.3%` / `83.95%` |
| 耗时 | ≥1000ms 转秒保留 2 位 | `7.87 s` / `473 ms` |
| 缺失值 | 统一用 em dash `—` | 失败任务 MAPE 显示"—" |

> `UX-CPY-08`：**缺失值一律用"—"，禁止用 0 或空白代替**。0 与"未知"在业务上含义完全不同。

## 12. 交付、一致性与后续规划

### 12.1 设计系统落地建议（技术栈落差）

**落差事实**：PRD §6.2 与 `Q16`/`Q17` 约定的前端技术栈是 **React + TailwindCSS + Ant Design + ECharts**；而本高保真原型是 **纯静态 HTML + 手写 CSS（`app.css`）+ 自研 SVG 图表（`charts.js`）**。二者不是同一套实现，需要一次**设计系统移植**。

映射建议：

| 原型资产 | React 实现落点 | 迁移注意 |
|---|---|---|
| `app.css` 令牌（56 个） | `:root` + `[data-theme="dark"]` 或 Tailwind `theme.extend` | 保留 `oklch()`；Tailwind 3.4+ 支持 oklch 任意值 |
| 组件类（`.btn` / `.card` / `.badge` …） | Ant Design 组件 + 少量自定义 Token overrides | 优先用 AntD 的 `ConfigProvider.theme.token` 覆盖主色/语义色，而非重写组件 |
| 自研 SVG 图表 | **ECharts**（`Q16` 建议） | 须复刻"历史实线 + 预测虚线 + 置信带 + 预测起点标注"的视觉编码 |
| `demo-data.js` 示例数据 | 由真实 API 替代 | `REAL_EVAL` 仅用于原型演示，实现时删除 |
| `charts.js` | 删除，改 ECharts | — |

> `UX-GOV-02`：**令牌是唯一真源**。React 实现时须把 `app.css` 的令牌值**完整搬入** `ConfigProvider` / CSS 变量，不得在组件内散落硬编码颜色，否则本次无障碍修复成果会失效。
> `UX-GOV-02a`：ECharts 主题须注册为自定义 theme，读取同一套 CSS 变量，保证图表色随主题切换（原型已实现自动重绘，实现时须保留该能力）。

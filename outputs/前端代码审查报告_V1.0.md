### 🔴 D-02【高】执行页「五阶段进度」回放恒不推进（StrictMode + `bootRef` 空依赖陷阱）
**等级**：高 · **可复现**：是 · **位置**：`web/src/pages/RunningPage.tsx:177-195`

**现象**：执行页的「总体进度」卡进度条恒为 **0%**、永远显示「阶段 1/5」、阶段列表中第 1 阶段永远「进行中」——与该卡上方「**任务已完成**」的结论自相矛盾。

**证据**（在**代理正常**的 5190 上复现，故与 D-01 无关；任务 57 后端状态确为 `succeeded`）：

| 采样时刻 | 页面 `data-phase` | 进度条宽 | 阶段文案 | 第 1 阶段状态 |
|---|---|---|---|---|
| 0.9 s | succeeded | **0%** | 阶段 1/5 | 进行中 |
| 2.1 s | succeeded | **0%** | 阶段 1/5 | 进行中 |
| 4.6 s | succeeded | **0%** | 阶段 1/5 | 进行中 |

任务已知终态、预算列已算出真实值（0.0/0.3/0.5/1.8/0.3 s），但回放 4.6 秒零推进。

**根因**（`RunningPage.tsx:177`）：
```ts
useEffect(() => {
  if (bootRef.current) return;       // ← 第二次执行直接退出
  bootRef.current = true;
  ...timers.push(window.setTimeout(() => setRevealed(i), ...));
  return () => timers.forEach((t) => window.clearTimeout(t));
}, []);                              // ← 空依赖
```
React 18 **StrictMode 在开发态会 setup → cleanup → setup**：第一次 setup 排好了 5 个定时器，紧接着的 cleanup **把它们全部清掉**；第二次 setup 因为 `bootRef.current === true` **直接 return**，定时器再也不会被重建 → `revealed` 永远停在 `0`。
（`main.tsx` 已启用 `<React.StrictMode>`，故开发态必现；生产构建无 StrictMode，不受影响 —— 属**开发期可见、但误导性很强**的缺陷。）

**修复**：让"只播一次"的语义不依赖"跳过第二次 setup"。两种可行写法：
1. 去掉 `bootRef`，改依赖 `[wallMs]` + 一个"已播过"标志位（但需允许 cleanup 重建定时器）；
2. 保留空依赖，但把守卫与排程解耦：cleanup 里若检测到"尚未真正播完"则重排程；
3. 最简：把 `bootRef` 判断改为"只在 `revealed === 0 且 timers 为空` 时跳过"，并把 `timers` 提到 ref 上。

### 🔴 D-03【高】结果页空态「调整参数重跑」链接必坏（参数名写错 + 值恒空）
**等级**：高 · **可复现**：是 · **位置**：`web/src/pages/ResultPage.tsx:131`

**现象**：在「任务不存在 / 失败」空态点「调整参数重跑」，**必然**落到参数页的报错态「无法进入参数配置 · 缺少 datasetId 参数」。

**证据**：
```

```

**两处缺陷叠加**：
1. **参数名不匹配** —— 链接用 `dataset_id`，而 `ParamsPage.tsx:111` 只认 **camelCase `datasetId`**（`params.get('datasetId')`）；

（两份可对照的正确写法在同仓库：`UploadPage.tsx:384`、`RunningPage.tsx:716` 都用的是 `datasetId`。）

**修复**：把「重跑」改为跳 `/upload`（数据不可知时最稳妥），或让 `API-19`/`API-14` 的失败响应回带 `dataset_id` 后再拼 camelCase 参数。

### 🟠 D-05【中】历史列表「任务总数」显示的是"当前页条数"，与分页器自相矛盾
**等级**：中 · **位置**：`web/src/pages/HistoryPage.tsx:41 / 141 / 430`

**现象**：同一屏里，「任务总数」卡片与分页文案「第 X / Y 页，共 N 条」给出**两个不同的"总数"**。有 35 条任务时，卡片显示 `20`（当页条数），分页器显示 `共 35 条`。

**修复**：卡片改用接口返回的 `total`；若确要保留当页口径，标签必须显式写「本页任务 / 本页均值」。

### 🟠 D-06【中】接口返回非预期报文时静默挂起，故障被完全掩盖
**等级**：中 · **可复现**：是（本报告 D-01 就是被它掩盖的） · **位置**：`web/src/api/client.ts:98-105` + `web/src/pages/ResultPage.tsx:111 / 151`

**现象**：当接口返回的不是 `{code,message,data}` 信封（例如 D-01 里返回的 HTML），页面**不会**给出任何错误提示，而是**永久停在「正在加载预测结果…」**。这正是 D-01 难以被用户/开发者察觉的原因。

**根因**（两段代码合起来构成静默失败）：
1. `client.ts:101` `if (body.code !== 0)` —— 当 `body` 是字符串（HTML）时 `body.code` 为 `undefined`，`undefined !== 0` 成立 → 抛 `new ApiError(undefined, undefined)`，**message 丢失**；`unwrap` 没有校验信封形状。
2. `ResultPage.tsx:111` 用**字符串真值性**当错误判别：`if (error)`。当错误信息为空串（`Error.message` 为 `''`）时，`error` 为 falsy → 不走错误分支；`:151` 的 `if (loading || !data)` 又把 `data === null` 当作「加载中」→ 页面永远显示 loading。

**修复**：
- `unwrap` 先校验信封（`typeof body !== 'object' || body === null` → 抛带明确文案的 `ApiError`，如「服务返回了非预期内容（可能未连到后端）」）；
- 页面用**显式状态枚举**（`'loading' | 'ready' | 'error'`）而非字符串真值性做判别。

### 🟠 D-07【中】`npm run lint` 当前失败：ESLint 未忽略 Vite 依赖缓存 `.vite/`
**等级**：中（CI/质量门禁失效） · **可复现**：是 · **位置**：`web/eslint.config.js:11`

**症状升级**：用户截图显示**整页布局崩坏**（两栏 hero 塌成堆叠、文字被左边缘裁切、出现横向溢出）。

**证据链**：
| 检查 | 修复前 | 修复后 |

**根因（`data/tmp/vite.log` 第 75-79 行）**：
```
11:26:58 [vite] changed tsconfig file detected ... Clearing cache and forcing full-reload
11:26:58 [vite] page reload tailwind.config.js
11:26:58 [vite] vite.config.ts changed, restarting server...
```

### 🔑 由此得到的运维纪律

> **`vite.config.ts` / `tailwind.config.js` / `postcss.config.js` / `tsconfig.json` 这类构建配置，一旦"批量改动"或被外部工具重写，必须手动重启 dev server 并复查两项：**
> 1. `curl -s <前端端口>/api/v1/... | head -c 60` → 必须是 JSON（验证代理）；
> 2. `curl -s <前端端口>/src/styles/index.css | wc -c` → 必须是**万字节级**（验证 PostCSS 已编译；若只有几千字节且含原始 `@tailwind`，说明未编译 → 全站布局会崩坏）。
>
> **Vite 的自动重启在配置被并发改写时可能只重启成功一半**，且不会在页面上报错 —— 这是本次两个缺陷（D-01 与布局崩坏）的共同来源。
